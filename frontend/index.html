How measurements are taken

All algorithms run in Python on the backend. The browser only sends input and draws the returned steps, so drawing never affects the timings.

Time

Each run is timed with time.perf_counter_ns() while Python's garbage collector is paused. The run is repeated and the median is reported, together with mean, standard deviation, minimum and maximum. Step recording for the visualisation is switched off during timing.

One search takes well under a microsecond, which is too short to time on its own. Single searches are therefore timed as a loop of 1,000 identical searches and divided by 1,000. Benchmarks time a batch of searches (half present keys, half absent) and report the time for one search.

Memory

Memory is measured in a separate run under tracemalloc, which reports the peak amount of memory Python allocated during the call. For AVL search this includes building the tree, because the tree is extra memory the algorithm needs. Binary search works directly on the sorted input, so its extra memory is close to zero.

Database time

When input is loaded from Neo4j, the load time is measured and shown separately as “Neo4j load”. It is never added to the algorithm time.

Correctness

Benchmarks cross-check results: search hits are compared with Python set membership, and the shortest distances of every graph algorithm are compared with the first algorithm that ran on the same graph. The backend also has unit tests based on textbook examples (CLRS figures 24.4 and 25.4).

Interpreting results

Timings depend on the machine, the Python version and the input. Pure Python adds a large constant cost per operation, so two algorithms with the same complexity can differ by a constant factor. Compare growth across sizes rather than single numbers, and report the environment shown under each benchmark.
